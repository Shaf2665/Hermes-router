## What the evidence establishes

The [homepage](https://www.omniroute.online/) markets 352 providers, 19 routing strategies and 35 integrations. The [release README](https://github.com/cheaper-inference/OmniRoute/tree/release/v3.8.53) reports 380, 20 and 39 respectively; its older repository description still says 375 providers. These counts include different kinds of integrations, not just interchangeable chat backends. Freeze a version and capability definition before claiming parity.

The homepage says a new installation has a working keyless auto route. The README explicitly warns a fresh installation may have no eligible keyless target. Hermes should show actual configured readiness instead of promising a free working model.

Compression percentages, fallback speed and model quality on these pages are vendor claims. They do not establish that OmniRoute is faster than Hermes, or that adopting its features improves output quality.

The [license](https://github.com/cheaper-inference/OmniRoute/blob/release/v3.8.53/LICENSE) is MIT, copyright 2026 diegosouzapw. It requires preserving the copyright and permission notice in copies or substantial portions. This research proposes original Hermes implementations; if code is later reused, retain the required notices and check third-party components separately.

## Important product distinctions

- `auto/offline` in OmniRoute's docs means quota headroom, not guaranteed local-only inference. Hermes should label any local-only control unambiguously and fail closed if locality is promised.
- Auto-Combo docs describe fail-open capability/tier filtering when no candidate matches. This should not be copied into explicit user privacy, provider-scope or budget restrictions.
- Additional models, speculative fan-out, memory retrieval and lossy compression can increase latency, cost or wrong answers. Implementing all options does not itself improve performance.
- Source spot-checking confirms structures, not end-to-end behavior across every provider. Homepage/release/main documentation drift means even this inventory needs a pinned acceptance baseline.

## Recommended order for Hermes

The user selected both personal and team use, with a simple personal mode. Keep one gateway and progressively expose team governance rather than ask beginners to configure an organization.

| Disposition | Feature families |
|---|---|
| Reuse | Existing Python gateway, chat/Messages/embeddings, key pool, failover, cache, metrics, CLI, VS Code provider and Astro site. |
| Improve | Connection onboarding, dashboard accessibility/navigation, Windows installation, route transparency, measurement, concurrency/cancellation, model metadata, admin/inference authorization and team budgets. |
| Add | Responses and additional client adapters, compatible-provider setup, connection diagnostics, client configuration helpers and team governance missing from current Hermes. |
| Optional by default | Lossy compression, memory, media bridges, model panels/pipelines, guardrails that alter payloads, MCP/A2A/agent actions, plugins, external caches and sidecars. Optional does not mean omitted from parity tracking. |
| Later staged work | Broad provider-auth coverage, full media/Files/Batch/search surface, desktop/PWA/Android packaging, localization, cloud orchestration, advanced studios and ecosystem integrations. Each remains an explicit full-scope backlog item. |

1. **Measure and remove friction:** deterministic local upstream benchmark, concurrent streaming/cancellation and failover tests, installation checks, truthful empty states, connection test, copyable client configuration, accessible dashboard and matching website instructions.
2. **Make current routing trustworthy and understandable:** preserve existing default; simple speed/cost/locality choices; real model metadata; route explanation; strict admin separation, budget enforcement and private-key handling; bounded background health work.
3. **Close important compatibility gaps:** Responses streaming/tool calls, then selected Gemini/Ollama adapters and custom compatible upstreams; client-config fixtures and migration checks.
4. **Add opt-in capabilities in separately testable increments:** larger protocol/media surface, provider-specific auth, compression with fidelity evaluations, memory, MCP/A2A and advanced routing.
5. **Complete remaining parity workstreams visibly:** plugins, agent orchestration, device packaging, localization, cloud management and optional infrastructure. Track each as implemented/tested, partial, or not implemented. Do not call phase 1 full parity.

These priorities are engineering recommendations, not changes to the user's requested full scope. Acceptance should measure time to first successful request, gateway-only p50/p95 overhead, stream time to first token, throughput/RSS under a fixed workload, failover correctness, and configuration steps. Compare against the same OmniRoute version, hardware, upstream fixture and cache conditions before claiming Hermes is faster.
